Op acknowledgement latency

measured against the local WAL fsync, not Postgres

Log-spaced buckets, HDR-style — a linear histogram spends all its resolution on the common case and none on the tail, which is the only part anyone cares about. p99 is the number. A p50 of 2 ms with a p99 of 400 ms is a keystroke that visibly stalls several times a minute.

Op buffer depth

leading indicator — latency is the lagging one

The bounded ArrayQueue between the session loop and the flush task. Depth rising means the flusher is losing; the amber band is where back-pressure engages and the session loop starts waiting. Watching this catches a stall a few seconds before the latency histogram does.

Editor core bundle

downloaded before anyone can type

Squarified treemap over the twiggy output. The grammars are the interesting cell: syntax highlighting is a third of the bundle, and it is the one part that could load on demand — nobody opens a code block in the first second.

Where a keystroke goes

one op, applied locally then flushed — width is time

The wide frame is fsync, and that is correct rather than a problem: the client is acknowledged once the write-ahead log is durable, which is what makes an acknowledgement mean something. Moving it off the critical path would make the editor feel faster and be lying.
