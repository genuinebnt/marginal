How the sketches work

three structures, running live, each beside the exact answer

The sketches are the privacy mechanism, not a flourish. A conventional dashboard answers “how many distinct collaborators” by storing a row per person per session. HyperLogLog answers it from 64 bytes containing no identities, and Count-Min counts page edits without ever storing a page. You cannot leak what you never stored — and memory stays constant however large the workspace grows. Bounded error is the price, and it is shown below rather than hidden.

●HyperLogLog

Counts distinct collaborators in 64 registers. Each register keeps the longest run of leading zeros seen in a hashed id — a rare run implies many distinct items. Identity is never retained.

●Count-Min Sketch

Frequencies in a fixed 4×24 table. Each item increments one cell per row; the estimate is the minimum across rows, because collisions can only inflate. Never under-counts, sometimes over-counts.

●t-digest

Percentiles from ~24 adaptive centroids. Clusters stay fine-grained at the tails and coarse in the middle, which is the opposite of a fixed-bucket histogram and better where the tail matters.

Two percentile structures, deliberately

perf.html measures op latency with log-bucket HDR histograms; this page uses t-digest. Same problem, different trade: HDR has fixed buckets and a hard error bound at any percentile, trivial merging, and a memory cost you pick up front. t-digest adapts its centroids so accuracy concentrates at the extremes, which is better for p99.9 and worse for reasoning about the worst case. Implementing both and knowing which to reach for is the point.

Half real. The event stream is synthetic and seeded, so the same run happens every load. The three sketches are genuine implementations consuming that stream, and every estimate is shown next to the exact answer — a sketch that hides its error is indistinguishable from a wrong number.
