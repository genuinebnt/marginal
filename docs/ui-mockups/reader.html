Collaborative editing spec

Updated 2 hours ago · 6 min read · 1,284 ops since the last snapshot

The editor never mutates the block tree directly. Every keystroke, paste, and drag compiles to an operation, which is applied locally for instant echo and appended to the log for durability and sync.1

1 A footnote is a block kind. Whether it renders here or at the bottom is a rendering choice over the same tree — switch to Wide and watch it move without anything stored changing.

Why a block tree, not text

A markdown document is parsed on every render, so two people editing it must reconcile text. A block tree is parsed once at input time, so two people editing it apply operations to nodes. That is the whole reason live collaboration works here and merge-conflict UI never appears.

Marginal parses once, at input time, and stores the tree. There is no text to re-parse and no ambiguity to re-resolve per keystroke.

The representation boundary

spans is storage; rope + anchored marks is the working format. Exactly one conversion site each way, and span array indices are not stable under concurrent edit.2

2 Which is why every operation addresses content by anchor rather than integer offset — the single most important correctness detail in the model. 
enum Op {
    InsertText { block: BlockId, at: Anchor, text: String },
    DeleteText { block: BlockId, range: AnchorRange, text: String },
}

What the reader controls

Everything in the tools panel — column width, typeface, size, line spacing, focus mode — is view state. None of it touches the document. Two people reading this page at the same time can hold completely different settings, and neither sees the other's.

  • Width changes the measure, not the content
  • Typeface and scale are per-reader, stored against your account
  • Focus mode hides the rails and nothing else
◆
If a width change altered the tree, the design would be wrong. Try every control in the tools panel — the document underneath is identical throughout.
